## 2. 刷新流程

**第一步：跑脚本比对官方原文**

```bash
python -I scripts/fetch_official_rules.py
```

| 输出 | 含义 | 动作 |
|---|---|---|
| `UNCHANGED` | 官方《社区规范》内容哈希未变 | 直接用 `official-community-rules.md` 作依据 |
| `CHANGED` | 官方内容已更新，脚本会给出新旧哈希 | 读官方原文差异，补充检索，确认后 `--update` |
| `FETCH_FAILED` | 接口异常（超时、结构变更、code≠0） | 如实说明，转第二步检索，结论标注「官方原文未核验」 |

第一版快照由该脚本生成（2026-11-05，内容哈希 `d93b64afc569c97f`）。

**第二步：检索官方增量（覆盖接口拿不到的部分）**

接口只覆盖《社区规范》。公约 2.0、专项治理公告、新规解读要用检索补。用当年当月替换 `<YYYY-MM>`，一次跑 2-3 条：

```
小红书 社区规范 最新 更新 <YYYY-MM>
小红书 违禁词 治理 公告 薯管家 <YYYY-MM>
小红书 <品类> 内容规范 新规 <YYYY-MM>
```

命中官方或权威转载时，比对三点：发布日期、生效日期、是否与本地快照冲突。只采信能追到「薯管家 / 小红书官方 / 创作者中心」的表述；自媒体总结只能用来发现线索。

**第三步：探活官方页面（可选）**

```bash
for u in "https://www.xiaohongshu.com/crown/community/agreement" \
         "https://pgy.xiaohongshu.com/help/home" \
         "https://ad.xiaohongshu.com/help/docs"; do
  printf '%-60s ' "$u"
  curl -sS -m 15 -o /dev/null -w 'http=%{http_code}\n' -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64)" "$u"
done
```

这一步只用于发现入口迁移或下线：页面返回 `200` 不代表规则有更新，正文也抓不到。

**第四步：更新快照**

- 官方原文有变：`python -I scripts/fetch_official_rules.py --update`（会重写 `official-community-rules.md` 与哈希）
- 有新的专项规则：改 `platform-rules-snapshot.md` 对应条目 + 顶部日期 + 变更记录
- 有新词：补进 `banned-words.md` 或 `sensitive-topics.md`

## 4. 失效与异常判定

| 现象 | 判定 | 动作 |
|---|---|---|
| 脚本打印 `FETCH_FAILED` | 接口异常 | 读 stderr 的异常类型；转检索，结论标注「官方原文未核验」 |
| 接口返回 `code≠0` 或结构变更 | 接口改版 | 同上，并按 `github-network-and-api-fallback` 的思路定位（先看响应体，不猜） |
| 官方页 `http=000` 或超时 | 入口不可达 | 换 WebSearch 检索，结论标注「官方页未核验」 |
| 官方页 200 但正文是空壳 | 正常（SPA，正文靠 JS 渲染） | 不视为失败；规则原文走接口，不指望页面 HTML |
| 检索结果全是自媒体、无官方出处 | 依据不足 | 沿用快照，结论标注「本次未取得官方增量」 |
| 检索到与快照冲突的新规 | 规则变更 | 以官方发布日期为准，更新快照并在结论中提示 |
| 快照 > 90 天且本次刷新失败 | 时效风险 | 结论顶部写明「依据 X 月快照，可能滞后」，让用户决定 |

## 5. 红线

- 官方接口原文优先于一切检索摘要；两者冲突时以接口为准，并在结论里说明矛盾点。
- 审核结论必须能指出依据来自哪条规则；指不出就降为「建议」，不要凭印象判「阻断」。
- 自媒体文章里的「违禁词清单」常混入非官方口径，采信前先看它是否引用官方原文。
- 平台规则与《广告法》《化妆品监督管理条例》等法规同时适用，法规优先于平台口径。
